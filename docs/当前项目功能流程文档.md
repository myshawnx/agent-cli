# 当前项目功能流程文档

本文档根据当前仓库代码、目录、脚本和测试整理 `agent-cli` 的完整功能流程。它是一份事实文档：说明当前实现了什么、入口在哪里、数据如何流转、哪些测试覆盖了关键行为，以及当前实现边界是什么。

## 1. 项目定位

`agent-cli` 是一个本地优先的命令行编码助手，对外可执行命令为 `agent`。项目不 fork pi，而是把 pi 作为 SDK/runtime 使用：

- `@earendil-works/pi-coding-agent`：agent session、工具调用、TUI、session 管理、ResourceLoader、扩展事件。
- `@earendil-works/pi-ai`：模型解析、usage、faux provider。
- `@earendil-works/pi-tui`：交互式终端 UI。

本项目在 pi 之上实现的能力包括：

- CLI 命令层：`ask/init/resume/history/trace/diff/undo/review/eval/mcp`。
- `.agent/` 项目本地配置：policy、profile、memory、MCP、eval baseline。
- 运行时扩展链：policy gateway、loop guards、trace recorder、bash timeout、remember、MCP adapter。
- 审批模式：`readonly`、`suggest`、`workspace-write`、`auto`。
- 安全策略、循环保护、trace 投影、MCP 集成、eval 回归、demo/release 脚本。
- C6 硬化项：三支柱联调、command timeout、SIGTERM 失败保全、token budget soft-stop、MCP schema-map、持久 stdio client、pi-ai 去重。

入口文件是 `src/main.ts`。构建产物是 `dist/cli.js`。`package.json` 声明：

```json
{
  "bin": {
    "agent": "dist/cli.js"
  },
  "engines": {
    "node": ">=22.19.0"
  }
}
```

## 3. CLI 总入口

`src/main.ts` 调用 `createProgram()` 并执行 `program.parseAsync()`。命令定义集中在 `src/cli/args.ts`。

公共运行参数：

- `--cwd <path>`：工作目录，默认 `process.cwd()`。
- `-p, --print`：非交互 print 模式。
- `--model <id>`：模型 id。
- `--mode <mode>`：审批模式，默认 `suggest`，可选 `readonly | suggest | workspace-write | auto`。

默认命令和 `agent ask` 都会把命令行文本与管道 stdin 合并：

1. 命令行参数按空格拼接。
2. `readPipedStdin()` 在 stdin 非 TTY 时读取管道输入。
3. 两者同时存在时用空行拼接。
4. 两者都为空时，默认命令显示 help；`ask` 输出 usage 并返回错误码。

所有 command action 都通过 `runWithCliError()` 包装：

1. 命令函数返回数字退出码。
2. 异常写到 stderr。
3. 出错时设置 `process.exitCode = 1`。

## 4. 命令功能流程

### 4.1 默认命令和 `agent ask`

入口：`src/cli/commands/ask.ts`

命令：

```bash
agent "任务描述"
agent -p "任务描述"
agent ask "问题"
agent ask -p "问题"
```

流程：

1. 调用 `loadAgentConfig(cwd)` 读取 `.agent/policy.json`、`.agent/project-profile.json`、`.agent/memory.md`，缺失或格式错误时回退默认值并返回 diagnostics。
2. profile 选择顺序：`loadProfile(cwd)` -> config 中的 profile -> `detectProfile(cwd)`。
3. memory 读取 `.agent/memory.md`。
4. 构造 `ProjectContext`：`cwd`、`mode`、`policy`、`profile`、`memory`、`goal`。
5. 如果 `policy.sandbox.enabled === true`，只输出 warning；当前不启用 OS sandbox。
6. 非 print 模式调用 `driveInteractive()`，交给 pi TUI runtime。
7. print 模式构建 `resourceLoader`，`await resourceLoader.reload()`，再通过 `buildSession()` 创建 bare session 并调用 `drive()`。

print 模式下如果模型不可用或 API key 缺失，`runAsk()` 捕获异常，输出友好提示并返回 `1`。

### 4.2 `agent init`

入口：`src/cli/commands/init.ts`

命令：

```bash
agent init
agent init --force
```

流程：

1. 目标目录为 `.agent/`。
2. 如果 `.agent/project-profile.json`、`.agent/memory.md`、`.agent/policy.json` 任意存在，且没有 `--force`，命令提示已存在并返回 `0`。
3. 调用 `detectProfile(cwd)` 检测项目语言、包管理器、框架、测试框架、源码目录、测试目录、常用命令。
4. 写入 `.agent/project-profile.json`。
5. 在缺失或 `--force` 时写入 `.agent/memory.md` 骨架和 `.agent/policy.json` 默认策略。
6. 输出 profile 摘要和写入结果。

`agent init` 不生成 `.agent/mcp.json`。MCP 配置由 `agent mcp add/remove` 维护。

### 4.3 `agent resume`

入口：`src/cli/commands/resume.ts`

命令：

```bash
agent resume <session-id>
agent resume <session-jsonl-path>
agent resume <session-id> -p "继续处理"
```

流程：

1. 如果参数是存在的文件路径，直接作为 session 文件。
2. 否则调用 `SessionManager.list(cwd)`，按 `id` 或 `path` 匹配。
3. 找不到时输出错误并返回 `1`。
4. 用 `SessionManager.open(sessionPath, undefined, cwd)` 打开历史 session。
5. 重新读取当前 cwd 的 `.agent/` 配置、profile、memory。
6. 非 print 模式调用 `driveInteractive()` 重新打开 TUI。
7. print 模式如果没有 follow-up prompt，只输出解析到的 session 路径和提示。
8. print 模式如果有 prompt，重建 resource loader/session 并调用 `drive()`。

### 4.4 `agent history`

入口：`src/cli/commands/history.ts`

流程：

1. 调用 `SessionManager.list(cwd)` 获取当前 cwd 的 pi sessions。
2. 如果为空，输出 `No pi sessions found for this cwd.`。
3. 否则按修改时间倒序输出 Markdown 列表。
4. 每条包含 session id、修改时间、message 数、摘要、session 文件路径。

### 4.5 `agent trace`

入口：`src/cli/commands/trace.ts`、`src/trace/projection.ts`

命令：

```bash
agent trace
agent trace <session-id>
agent trace <session-jsonl-path>
```

流程：

1. 有参数时按文件路径、session id、session path 解析。
2. 无参数时取当前 cwd 最近一次 session。
3. `SessionManager.open()` 打开 session。
4. `projectTask()` 从当前 branch 读取自定义 trace entries 并投影成 `TaskView`。
5. 输出 Markdown 摘要：goal、mode、status、started/ended、turns、tool calls、modified files、session path。

该命令只读，不启动模型和 agent loop。

### 4.6 `agent diff`

入口：`src/cli/commands/diff.ts`

流程：

1. 执行 `git diff -- .` 读取 unstaged diff。
2. 执行 `git diff --cached -- .` 读取 staged diff。
3. 两者都为空时输出 `No file diff in the current worktree.`。
4. 否则输出 `# Agent Diff`，并按 `Staged`、`Unstaged` 分段显示。

### 4.7 `agent undo`

入口：`src/cli/commands/undo.ts`

流程：

1. 输出说明：只回退文件变化，不能撤销命令副作用。
2. 执行 `git status --porcelain` 判断工作区是否有变更。
3. 没有变更时输出 `No file changes to undo.`。
4. 有变更时执行 `git stash push --include-untracked -m agent-cli-undo-<ISO 时间>`。

当前实现不做 `git reset`，也不直接删除文件。

### 4.8 `agent review`

入口：`src/cli/commands/review.ts`

流程：

1. 读取 staged 与 unstaged diff 的 name-status。
2. 无 diff 时输出 `# Agent Review` 和 `No git diff found.`。
3. 对每个变更文件构造模拟 `write` 工具调用。
4. 调用与运行时相同的 `classify()` 做 policy 风险分类。
5. 检查 diff 中是否包含 test/spec 文件。
6. 输出 Markdown：mode、changed files、每个文件的 allow/confirm/deny、测试覆盖信号、建议说明。

该命令不启动模型，不启动 pi session。

### 4.9 `agent eval`

入口：`src/cli/commands/eval.ts`、`src/eval/harness.ts`

命令：

```bash
agent eval
agent eval --provider faux
agent eval --provider real --scenario <id>
agent eval --update-baseline
```

流程：

1. 从 `eval/fixtures/scenarios.json` 加载场景。
2. 按 `--scenario` 过滤场景；找不到时抛错。
3. 把场景对应 fixture 复制到系统临时目录。
4. 对临时目录做 baseline 文件快照。
5. `provider=faux` 时直接应用场景中的 `fauxPatch`。
6. `provider=real` 时在临时目录构造 `ProjectContext`、resource loader、session，并真实调用 `session.prompt(scenario.prompt)`。
7. 计算 changed files。
8. 执行 checks：`bugLocated`、`testsPass`、`diffTouches`、`addedTest`、`inBounds`。
9. 输出 Markdown 报告。
10. `--update-baseline` 会写 `.agent/eval/baseline.json`。
11. 所有场景通过返回 `0`，否则返回 `1`。

当前 `eval/fixtures/scenarios.json` 有 `hono-health-header` 场景。`provider=faux` 是确定性文件补丁路径，不等同于真实 agent loop；`provider=real` 会真实跑 headless session，可能消耗 token 并受模型漂移影响。

### 4.10 `agent mcp`

入口：`src/cli/commands/mcp.ts`、`src/mcp/config.ts`

命令：

```bash
agent mcp list
agent mcp add <name> --command <cmd> --args "..."
agent mcp remove <name>
```

流程：

1. 配置文件固定为 `.agent/mcp.json`。
2. `list` 读取配置并输出 server 列表；没有配置时输出配置文件路径。
3. `add` 写入或更新一个 stdio MCP server。
4. `remove` 删除一个 server；不存在时输出未配置提示。
5. `--args` 用简单分词规则解析，支持单引号、双引号和空格拆分。

该命令只维护配置。MCP 工具真正注册发生在非 `readonly` 会话的 `session_start`。

## 5. `.agent/` 本地数据

项目读取或写入以下本地数据：

```text
.agent/

  project-profile.json
  memory.md
  mcp.json
  eval/

```

### 5.1 `policy.json`

schema 位于 `src/config/schema.ts`：

```ts
{
  command: {
    allow: string[],
    confirm: string[],
    deny: string[]
  },
  path: {
    deny: string[],
    confirmWrite: string[]
  },
  limits: {
    maxChangedFiles: number,
    maxFixIterations: number,
    maxToolCalls: number,
    tokenBudget?: number,
    commandTimeoutMs?: number
  },
  sandbox: {
    enabled: boolean
  }
}
```

默认策略来自 `DEFAULT_POLICY_CONFIG`：

- `maxChangedFiles = 20`
- `maxFixIterations = 5`
- `maxToolCalls = 50`
- `commandTimeoutMs = 120000`
- `sandbox.enabled = false`
- 默认 deny/confirm/allow 命令和路径模式来自 `src/policy/types.ts`

`loadAgentConfig()` 不抛错。缺失、JSON 解析失败、schema 不符都会回退默认值并返回 diagnostics。

### 5.2 `project-profile.json`

字段包括：

- `language`
- `packageManager`
- `framework`
- `testFramework`
- `sourceDirs`
- `testDirs`
- `commands.test/lint/build`

检测逻辑位于 `src/context/profile.ts`，覆盖 TS/JS、Python、Go 常见项目；识别失败时退化为 `unknown` profile。

### 5.3 `memory.md`

`src/context/memory.ts` 负责：

- 读取 `.agent/memory.md`
- 渲染进 system prompt
- 由 remember 工具追加长期记忆

remember 工具追加格式是 Markdown 列表项。

### 5.4 `mcp.json`

结构位于 `src/mcp/types.ts`：

```ts
{
  servers: {
    [name: string]: {
      command: string,
      args?: string[],
      env?: Record<string, string>
    }
  }
}
```

文件缺失或 JSON 解析失败时，MCP 配置退回空 server 列表。

## 6. 运行时完整链路

### 6.1 ProjectContext

运行时统一上下文位于 `src/context/types.ts`：

```ts
{
  cwd: string,
  goal?: string,
  mode: ApprovalMode,
  policy: PolicyConfig,
  profile?: ProjectProfile,
  memory: string
}
```

默认命令、`ask`、`resume`、`eval --provider real` 都会构造该上下文。

### 6.2 system prompt 注入

`src/runtime/resource-loader.ts` 的 `buildInjectedSystemPrompt(ctx)` 会把 profile 和 memory 渲染文本追加到 pi 原始 system prompt 后面：

1. profile 由 `renderProfileForPrompt(profile)` 渲染。
2. memory 由 `renderMemoryForPrompt(memory)` 渲染。
3. `appendSystemPromptOverride` 使用 append，不替换 pi 原始 prompt。
4. pi 原生仍会加载 `AGENTS.md` 等自身上下文。

### 6.3 扩展链顺序

`buildExtensionFactories(ctx)` 顺序固定为：

1. `policyGateway(ctx.policy, ctx.mode, ctx.cwd)`
2. `loopGuards(...)`
3. `traceRecorder({ goal, mode })`
4. `commandTimeoutBash(ctx.cwd, commandTimeoutMs)`
5. `rememberTool(ctx.cwd)`
6. 非 `readonly` 时追加 `mcpAdapter(ctx.cwd, commandTimeoutMs)`
7. 最后追加调用方传入的 `extraFactories`

含义：

- policy 总是最先处理 `tool_call`。
- loop guard 和 trace 在同一 session 里记录预算、失败、工具调用和结果。
- bash timeout 通过重新注册 bash 工具包装执行。
- remember 是固定工具。
- MCP 仅非 `readonly` 注册，避免动态 MCP 工具绕过 readonly 硬边界。
- extra factories 最后追加，主要供测试或外部注入使用。

### 6.4 session 创建和工具激活

实现位于 `src/runtime/session-factory.ts`。

默认模型：

- 未传 model 时，默认 `getModel("anthropic", "claude-sonnet-4-6")`。
- 传入 `modelId` 时按运行时字符串调用 `getModel("anthropic", modelId)`。
- 测试可直接传入 faux model。

`computeTools(mode)`：

- `readonly`：`read`、`grep`、`find`、`ls`
- 非 `readonly`：`read`、`grep`、`find`、`ls`、`edit`、`write`、`bash`、`remember`

工具激活规则：

1. `readonly` 创建 session 时传 `tools: computeTools("readonly")`。这是 pi 全局 allowlist，写/执行工具和动态 MCP 工具都不会出现。
2. 非 `readonly` 创建 session 时传 `noTools: "builtin"`，不传 `tools` allowlist。
3. session 创建后统一调用 `session.setActiveToolsByName(computeTools(mode))`。
4. 非 `readonly` 这样做是为了避免 pi 全局 `tools` allowlist 过滤 `session_start` 后动态注册的 `mcp__*` 工具。
5. MCP adapter 注册远端工具后，会再把这些 `mcp__*` 工具加入 active tools。

### 6.5 print 模式驱动

实现位于 `src/runtime/driver.ts` 的 `drive()`。

流程：

1. 只接受 `printMode=true`。
2. 订阅 session events。
3. 监听 `SIGINT` 和 `SIGTERM`。
4. 调用 `session.bindExtensions({})`，确保 `session_start` 扩展在 bare session print 路径执行。
5. 调用 `session.prompt(prompt)`。
6. assistant `text_delta` 流式写入 stdout。
7. 如果没有流式 delta，用 `session.getLastAssistantText()` 兜底。
8. `agent_end` 时可通过 `onUsage` 上报 usage。
9. 正常结束输出换行。
10. finally 中移除 signal listener、unsubscribe、`session.dispose()`。

失败保全：

1. SIGINT/SIGTERM 到来时追加 `abort-preserved`。
2. 同时追加 failed `task-result`。
3. modified files 来自 session branch 中的 `task-modified-file` entries。
4. 不回滚工作区 diff。

### 6.6 交互模式驱动

实现位于 `driveInteractive()`。

流程：

1. 构造与 print 模式一致的 profile/memory 注入文本。
2. 创建或接收 `SessionManager`。
3. 调用 `createAgentSessionServices()` 创建 pi services。
4. 通过 `resourceLoaderOptions` 注入扩展链和 system prompt append。
5. 创建 session 时沿用 readonly/non-readonly 的工具激活规则。
6. 调用 `createAgentSessionRuntime()`。
7. 创建 `InteractiveMode` 并执行 `interactive.run()`。

交互模式下 confirm 类 policy verdict 会通过 `ctx.ui.confirm()` 弹确认；print/no UI 下 confirm 会保守阻断。

## 7. 审批模式与 policy

支持模式：

| 模式 | 当前行为 |
|---|---|
| `readonly` | 创建 session 时传 pi `tools` allowlist，只激活 `read/grep/find/ls`；policy 仍防御性 deny 写入和 bash |
| `suggest` | 写入类工具存在，但 policy 对写入返回 confirm；无 UI 时阻断，有 UI 时确认后才执行 |
| `workspace-write` | cwd 内写入按 policy allow/confirm/deny；敏感路径、越界、confirmWrite 等走策略 |
| `auto` | confirm verdict 直接放行，但 deny verdict 仍硬阻断 |

`src/policy/engine.ts` 的 `classify()`：

- 读类工具：检查 repo root 外读取和 deny path。
- 写类工具：readonly deny；未知路径 confirm；deny path deny；repo root 外 confirm；confirmWrite confirm；超过 `maxChangedFiles` confirm；suggest confirm；否则 allow。
- bash：readonly deny；deny command deny；命中受保护路径 confirm；confirm command confirm；否则 allow。
- 未知工具：默认 confirm，包含 `mcp__*`。

`src/policy/gateway.ts`：

1. 在 `tool_call` 先调用 `applyCommandTimeout()` 修正 bash `input.timeout`。
2. 调用 `classify()`。
3. deny 写 `policy-deny` 并返回 `{ block: true }`。
4. confirm 在 `auto` 下放行。
5. confirm 在无 UI 下阻断，并写 `policy-deny`。
6. confirm 在有 UI 下调用 `ctx.ui.confirm()`；用户拒绝时阻断并写 `policy-deny`。
7. 写入类工具放行后增加 changed file 计数。

## 8. loop、trace、bash、remember

### 8.1 bash timeout

实现：`src/runtime/bash-timeout.ts`、`src/runtime/bash-timeout-core.ts`

行为：

1. `commandTimeoutBash()` 在扩展链中重新注册带 timeout 包装的 bash 工具。
2. `commandTimeoutMs` 是毫秒配置；pi bash input 的 `timeout` 是秒。
3. 执行前会把工具参数 timeout 限制在配置范围内。
4. 同时用 `AbortController` 在超时时中止执行。
5. 长跑 bash 集成测试断言会返回 `Command timed out after <秒数> seconds`。

### 8.2 loop guards

实现：`src/loop/guards.ts`

当前守卫：

- `maxToolCalls`：超过工具调用次数时阻断当前工具调用，写 `loop-guard`。
- `tokenBudget`：在 `message_end` 累计 assistant usage；达到预算后发送 soft-stop，并在下一次 `tool_call` 前阻断。
- reward-hacking guard：修测试类目标中，若目标没有表达新增/编写/更新测试，则阻断对测试文件的写入。
- patch locate failure：`edit` 或 `apply_patch` 定位失败时写 `patch-locate-failed`；无 UI soft-stop；有 UI 询问是否让 agent 重读并重试。
- no-progress：测试命令失败签名重复达到 `maxFixIterations` 时发送 soft-stop。

token budget 是软停止，不是 provider 请求前硬上限。

### 8.3 trace recorder

实现：`src/trace/entries.ts`

写入 entries：

- `task-meta`：`goal`、`mode`、`startedAt`
- `task-tool-call`：工具名和输入
- `task-modified-file`：写入类工具目标文件
- `task-result`：`completed`、`endedAt`、turns、toolCalls、modifiedFiles

print driver 在异常或 SIGINT/SIGTERM 时会补写 failed `task-result` 和 `abort-preserved`。

`src/trace/projection.ts` 从 pi session branch 投影出 `TaskView`，供 `agent trace` 使用。

### 8.4 remember 工具

实现：`src/tools/remember.ts`

工具名：`remember`

参数：

```ts
{
  note: string
}
```

执行时调用 `appendMemory(cwd, note)` 写入 `.agent/memory.md`，并追加 `memory-write` entry。

## 9. MCP 运行时

MCP 配置命令只写 `.agent/mcp.json`。真正运行时由 `src/mcp/adapter.ts` 在非 `readonly` session 的 `session_start` 中处理。

### 9.1 session_start 注册流程

1. 读取 `.agent/mcp.json`。
2. 对每个 server 创建一个 `McpStdioClient`。
3. 调用 `client.listTools()`；内部幂等启动子进程并完成一次 `initialize`。
4. 复用同一连接调用 `tools/list`。
5. 为每个远端工具生成安全工具名：`mcp__<server>__<tool>`，非法字符替换为 `_`。
6. 如果 `inputSchema` 顶层是 `object`，调用 `schema-map.ts` 映射到 TypeBox 子集。
7. 否则使用宽松 `Type.Record(Type.String(), Type.Any())`。
8. 用 `pi.registerTool()` 注册本地桥接工具。
9. 注册后调用 `pi.setActiveTools()` 把 `mcp__*` 加入 active tools。

### 9.2 工具执行流程

1. 本地 MCP 工具执行时复用该 server 的常驻 `McpStdioClient`。
2. `client.callTool(tool.name, params, signal)` 发送 JSON-RPC `tools/call`。
3. 请求按递增 id 发送。
4. 响应按 JSON-RPC `id` 路由到对应 pending request。
5. 每个请求有 timeout，默认来自 `policy.limits.commandTimeoutMs`。
6. AbortSignal 只 reject 当前请求并清理 pending，不关闭共享连接。
7. 成功结果转换为文本并用 `truncateTail(...).content` 截断到约 8KB。
8. 成功写 `mcp-tool-call` entry；失败写 `mcp-error` 并抛出。

### 9.3 连接生命周期

`src/mcp/stdio-client.ts` 当前是持久 stdio 连接模型：

- 每个 server 一个常驻子进程。
- `initialize` 只做一次。
- `tools/list` 和所有 `tools/call` 复用同一连接。
- 非 JSON stdout 行会被忽略。
- server 崩溃或提前退出会 reject 所有在途请求。
- adapter 的 `onClose` 会记录 `mcp-error`，并 best-effort 从 active tools 摘掉该 server 的工具。
- `session_shutdown` 会 dispose 所有 clients。
- print 路径的裸 `session.dispose()` 不保证触发 `session_shutdown`，所以 stdio client 注册了 `process.exit` hook 兜底回收 live children。
- 当前不做自动退避重连。

### 9.4 schema-map 范围

`src/mcp/schema-map.ts` 支持 JSON Schema 子集：

- `object`、`properties`、`required`
- `string`
- string enum
- `number`
- `integer`
- `boolean`
- `array`
- `description`

复杂结构回退宽松：

- `oneOf`
- `anyOf`
- `$ref`
- 缺失 `type`
- 递归分支
- 非对象顶层 schema

readonly 模式不注册 MCP adapter。这是安全边界设计；如果未来要 readonly MCP，需要 MCP 工具级 policy。

## 13. 典型完整链路

### 13.1 首次初始化

```bash
agent init
```

链路：

1. commander 分发到 `runInit()`。
2. 检测 profile。
3. 写 `.agent/project-profile.json`。
4. 写 `.agent/memory.md`。
5. 写 `.agent/policy.json`。
6. stdout 输出 profile 摘要。

### 13.2 readonly 只读问答

```bash
agent -p --mode readonly "总结这个项目结构"
```

链路：

1. 加载 `.agent/` 配置。
2. 构造 `ProjectContext`。
3. 扩展链不会注册 MCP adapter。
4. `buildSession()` 传 `tools: ["read","grep","find","ls"]`。
5. pi 全局 allowlist 形成硬边界。
6. print driver 触发 `session_start` 并执行 prompt。
7. 模型无法调用 write/edit/bash/remember/MCP 工具。

### 13.3 suggest 模式写入确认

```bash
agent --mode suggest "帮我修改这个文件"
```

链路：

1. 非 readonly session 用 `noTools: "builtin"` 创建。
2. `setActiveToolsByName()` 激活基础工具。
3. 模型提出 `edit/write` 时触发 `tool_call`。
4. policy classify 对 suggest 写入返回 confirm。
5. 有 UI 时弹确认；确认前不会进入工具 execute。
6. 无 UI print 模式下 confirm 保守阻断。

### 13.4 workspace-write 修复任务

```bash
agent --mode workspace-write "修复这个 bug"
```

链路：

1. 构造 `ProjectContext`。
2. 注入 profile/memory。
3. 注册 policy、loop、trace、bash timeout、remember、MCP。
4. 模型读文件、搜索、编辑、运行测试。
5. 每个工具调用先过 policy。
6. loop guards 检查预算、token、测试文件、patch locate、重复失败。
7. trace recorder 写 task entries。
8. 结束时写 completed `task-result`。

### 13.5 MCP 工具调用

```bash
agent mcp add stub --command node --args "server.mjs"
agent --mode workspace-write "调用 MCP 工具"
```

链路：

1. `agent mcp add` 写 `.agent/mcp.json`。
2. 非 readonly session 的 `session_start` 加载 MCP 配置。
3. adapter 为 server 创建持久 stdio client。
4. `initialize` + `tools/list`。
5. 工具注册为 `mcp__stub__<tool>`。
6. active tools 加入 MCP 工具。
7. 模型调用时先经过 policy 未知工具 confirm 逻辑。
8. adapter 复用同一 client 调 `tools/call`。
9. 成功写 `mcp-tool-call`。

### 13.6 中断失败保全

print 模式任务执行期间收到 SIGTERM：

1. driver 捕获 signal。
2. 从 session branch 读取 `task-modified-file` entries。
3. 写 `abort-preserved`。
4. 写 failed `task-result`。
5. `session.dispose()`。
6. 抛出包含“current diff preserved for handoff”的错误。
7. 工作区 diff 保留，不做 rollback。

## 15. 当前实现边界

- `policy.sandbox.enabled` 是配置字段；当前只 warning，不接 OS sandbox。
- bash 风险判断是字符串/glob 级 speed bump，不是完整 shell parser。
- bash 受保护路径检测是 best-effort，不覆盖全部 shell 语法。
- `commandTimeoutMs` 会中止 bash 执行并返回 timeout 错误；跨平台进程树终止仍按 best-effort 表述。
- `tokenBudget` 是 loop guard 软停止，不是 provider 请求前硬上限。
- `suggest` 当前是 confirm gate 方案，没有独立 `propose_patch` 工具。
- `undo` 只通过 git stash 保存/回退文件变化，不能撤销命令副作用。
- `resume` 同时支持交互恢复和 print 模式恢复；print 模式需要显式 follow-up prompt 才继续执行。
- `eval --provider faux` 是确定性 patch 路径，不是真实模型回放。
- `eval --provider real` 会真实执行 headless session，可能消耗 token 并受模型漂移影响。
- `.agent/mcp.json` 只能通过 MCP 命令维护，`init` 不生成。
- MCP 只在非 `readonly` 模式注册。
- MCP 参数 schema 只映射 JSON Schema 子集；复杂结构回退宽松透传。
- MCP 是持久 stdio 连接；server 崩溃会 reject 在途请求并 best-effort 摘掉 active tools；当前不做自动退避重连。
- MCP streaming 结果不增量转发；当前一次性返回并截断。
- faux-provider headless integration 依赖 `postinstall` 去重后的单一 `pi-ai` api-registry；禁用 lifecycle scripts 可能导致 faux provider 注册到错误 registry。
- 当前平台验证主要围绕 Node 22 和本地/CI 环境；Windows/macOS 进程树终止不写成完全等价承诺。
